기존 프로젝트에 설치할 때
기존 repo에서는 “덮어쓰기”보다 “관리 블록과 manifest를 확인”하는 감각이 중요합니다.
먼저 dry-run 성격으로 읽기설치가 만드는 파일과 managed block을 미리 확인합니다. 기존 팀 문서, 기존 AGENTS.md, 기존 planning 폴더와 충돌 가능성을 검토한 뒤 실제 설치를 결정합니다.
AGENTS.md는 공동 소유하네스가 관리하는 BEGIN/END managed block 안은 스크립트가 자동으로 갱신합니다. block 밖은 팀의 메모 영역으로 보존되어 자유롭게 적어둘 수 있습니다.
Planning은 canonical memory.planning/**은 프로젝트의 구조, 관례, roadmap, 검증 evidence를 모아두는 공식 기록입니다. 임시 메모는 .scratch/로 분리하여 핵심 기억과 섞이지 않게 합니다.
Live gate는 명령으로만.scratch/phase-state.json은 현재 작업을 열거나 막는 상태 파일입니다. 직접 편집하면 nonce가 어긋나 다음 harness check에서 drift 경고가 발생합니다.

설치 직후 확인
설치가 끝나면 바로 구현하지 말고, 두 명령으로 현재 상태를 읽습니다.

첫 점검

harness harness check harness next

check는 구조 오류, missing verification, managed block 누락, 단계 drift를 감지합니다. next는 지금 안전하게 할 다음 행동을 말합니다.

경고가 있으면

  • 경고가 가리키는 파일을 먼저 읽습니다.
  • may_edit=false면 코드를 수정하지 않습니다.
  • 승인 요청이 나오면 사람이 명시적으로 승인하기 전 멈춥니다.
  • JSON이나 상태를 해석할 수 없으면 구현을 시작하지 않습니다.

기본 작업 흐름
사용자는 “다음 행동 확인 → 안전 전환 → 검증”을 반복합니다.

일상 루프

harness check harness next harness run harness check

처음과 끝에 check를 둬서 상태 drift와 검증 누락을 초기에 잡습니다.

중요한 규칙

  • may_edit=false 상태에서는 애플리케이션 코드를 수정하지 않습니다.
  • 구현은 phase=execute, approved=true, allowed_paths가 맞을 때만 시작합니다.
  • 작업 중 범위가 커지면 구현을 멈추고 계획으로 돌아갑니다.

승인 gate
승인은 agent가 대신할 수 없습니다. 사람이 계획을 읽고 명시적으로 열어야 합니다.

범위 변경 코너 케이스
작업 중 새 책임이 생기면, 구현을 계속하는 것이 아니라 plan으로 돌아갑니다.

멈춰야 하는 신호

  • 새 파일/새 모듈이 필요하지만 allowed_paths에 없음
  • 테스트 명령이 계획과 맞지 않음
  • 수정 이유가 원래 acceptance criteria를 벗어남
  • 사용자가 중간에 목표를 바꿈

올바른 복귀

harness next로 현재 gate를 확인하고, plan을 갱신한 뒤 다시 사람 승인을 받습니다. 억지로 기존 계획에 끼워 넣으면 하네스의 의미가 사라집니다.

Rule: plan 밖 변경은 구현 밖으로 보낸다
