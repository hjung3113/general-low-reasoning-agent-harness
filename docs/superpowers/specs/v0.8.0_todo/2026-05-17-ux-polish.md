## Why deferred

v0.7 phase-gate-hardening intentionally adds ceremony (TTY-only gate, multi-CLI-verb flow, env-authorized CI path, transaction journal, audit chain) because the agent cannot be trusted. The protections are correct. The UX cost is real but a separate problem class. Bundling them into v0.7 would expand scope past one releasable phase.

After v0.7 lands and is dogfooded for ~1 sprint, the friction list below should be revisited with actual usage data.

---

## Friction observed in v0.7 (baseline to improve)

1. **IDE ↔ terminal context-switch per phase boundary** — TTY-only `phase approve` forces the user out of the IDE 3-4 times per phase. Cannot be relaxed without re-introducing the IDE-stdin capture footgun, so the fix is to make the round-trip faster, not skip it.
2. **Exit codes (6, 8, 11, 12, 14, etc.) are opaque** to users without the manual. Numeric exit codes are necessary for scripting; the human-facing message needs to carry the "do this next" instruction in plain language.
3. **Slash command naming** — `/fsd-run-phase` vs `/fsd-run-all` are similar; users with prior `/fsd-phase` muscle memory mistype. Tab-completion helps but doesn't eliminate.
4. **Three env vars surfaced** (`HARNESS_BY_TRUST`, `HARNESS_AUTOMATION`, `HARNESS_ALLOW_NETWORK`) — necessary for CI but visible in every grep of the design doc; users may feel they need to understand them even when they don't.
5. **`phase reopen --to <discuss|plan>`** — common operation buried in verb syntax. Conceptually it's "go back".
6. **Design doc length (749 lines)** — onboarding cost for new contributors / future maintainers is high. Implementation-level doc, not user doc.
7. **No single command answers "what do I run next?"** — user must read agent output, parse it for the exact `harness ...` line, copy to terminal.
8. **First-time installer is functional but unguided** — `python3 scripts/install_harness.py` prompts for target/profile/db/adapter without explaining trade-offs.

## Proposed v0.8 additions (sketch — refine before implementing)

### A. `harness status` (new verb)

Read state under lock; print structured human summary:

```
Phase: execute (entered 2026-05-17T10:30 UTC, 24m ago)
Approved: yes by alice@example.com at 10:20 UTC
Execution mode: manual
Autopilot: inactive
Next action: harness phase set done    (run when execute is complete)
```

Zero state mutation. Safe for the agent to invoke before deciding what to tell the user. Lifts cognitive load of "where am I?"

### B. `harness next` (new verb)

Print **exactly** the command the user should run next, one line, no fluff. Suitable for `$(harness next)` capture in shell aliases:

```
$ harness next
harness phase approve
```

If no action is needed (e.g. autopilot is mid-run): print "no action" and exit non-zero so shell aliases don't accidentally do something.

If TTY-only command is the next step and the caller is non-TTY: print the command but also a hint that the user must run it themselves.

### C. Error message standard (cross-cutting)

Every exit code carries a `message` and a `fix` line. Example:

```
$ harness phase approve
Error (exit 6): no gitconfig user.email and --by not provided.
Fix: run `git config user.email <your-email>` or
     `harness phase approve --by <your-email>`.
```

Round-4 design already moves toward this; v0.8 makes it a hard contract — every exit ≠ 0 must include a "Fix:" line. Smoke test asserts this.

### D. `/fsd-status` slash command

In-IDE phase visibility. Agent or user types `/fsd-status` in the IDE chat; harness CLI runs (via slash-command Markdown body) `harness status`; the agent surfaces the output. No TTY required (read-only).

### E. One-page cheatsheet

`docs/cheatsheet.md` — printable single page covering:
- 80% case: manual flow, 3 commands per phase, 1 command for reopen.
- 15% case: autopilot opt-in via slash commands.
- 5% case: CI (env vars), no-git mode, abort.

Linked from AGENTS.md.

### F. Onboarding walkthrough (`harness onboarding`)

Interactive 5-step first-time setup:
1. Pick adapter.
2. Pick profile / db.
3. Confirm gitconfig user.email.
4. Pick autopilot default posture (manual recommended).
5. Show "next: open your IDE and start a conversation. When the agent says 'approve', run `harness phase approve` in this terminal."

Runs after install. Skippable for power users (`--skip-onboarding`).

### G. Slash command alias / discovery

`harness slash list` prints all installed slash commands per adapter with one-line descriptions. Helps users recover from rename ("which one was it again?").

### H. Heartbeat surface

v0.7 heartbeat goes to stderr + `.harness/heartbeat.log`. v0.8: also write a single-line status to `.harness/CURRENT` that an IDE plugin (if/when written) can poll for live progress indicator.

### I. Autopilot dry-run

`harness phase autopilot start --dry-run` prints what would happen across the cascade (next N phases, budget, network posture, halt conditions) without mutating state. Lets the user audit the plan before unleashing the agent.

### J. Reopen UX

Rename / alias: `harness phase back` ≡ `harness phase reopen --to plan` (most common case). Full verb kept for explicit `--to discuss` usage. Both routed through the same code path.

## Open questions for when v0.8 starts

- Should `harness status` ALSO print autopilot progress (if active) — phase X of Y completed, remaining budget? Likely yes.
- Should `/fsd-status` and `harness status` share output format, or should `/fsd-status` be friendlier (Markdown-formatted)?
- Does `harness onboarding` write a one-time `.harness/onboarded.json` to know it ran? Or re-run on demand always?
- Should error messages carry localization hooks (i18n) or stay English-only? v0.8 likely English-only; defer i18n.
