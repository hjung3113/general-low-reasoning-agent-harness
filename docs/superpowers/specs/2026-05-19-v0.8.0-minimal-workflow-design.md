# v0.8.0 Minimal Workflow Design

Date: 2026-05-19
Status: design patch after Codex, gpt-5.5, and Claude adversarial review

## Goal

v0.8.0 reduces the normal operating surface from the v0.7.2 low-level phase machine to a navigator-style workflow.

The product direction is:

- normal users see at most four commands;
- the happy path uses no flags;
- adapters use the same high-level workflow concept, but through a conservative machine contract;
- low-level phase, nonce, trust, anchor, state-repair, autopilot, and release internals remain available only as advanced/debug/CI surfaces;
- approval, execute prerequisites, malformed state, adapter contracts, release checks, and security-sensitive flows remain hard boundaries.

## User-Facing Command Definition

A user-facing command is any command or documented alias that a normal human user or adapter happy path is expected to type to complete ordinary work.

Count it when it appears in the README quickstart, onboarding, normal manual path, adapter happy-path prompt, or slash-command list.

Do not count commands that are documented only in advanced/debug/CI/reference sections, release process docs, migration docs, or maintainer troubleshooting.

Flags are not counted as commands, but normal human happy-path commands must not require flags.

## v0.8.0 Command Surface

The normal user-facing surface is exactly four commands:

| Command | Normal role |
| --- | --- |
| `harness` | One-screen human dashboard: current state, next action, and whether the user is blocked. |
| `harness next` | Read-only recommender: prints the next safe action. |
| `harness run` | Performs the next high-level action when it is safe, or asks for visible human approval when approval is the next required boundary. |
| `harness check` | Runs the normal readiness/policy check with no flags. |

`harness mode` is rejected for v0.8.0. It explains an internal concept, but it makes the normal workflow five commands.

`harness status` is not part of the normal surface. Its human status behavior should be folded into bare `harness`; if the command remains for compatibility, it is advanced/reference only and must not be taught as a normal alias.

## Bare `harness` Semantics

Bare `harness` is read-only and never repairs, approves, or changes phase.

It must handle these states without tracebacks:

| State | Human result | Exit |
| --- | --- | --- |
| No harness state | One-screen first-run message with the normal next action. | non-zero |
| Malformed state | Hard error with plain-language corruption message and `harness check` as the normal next command. | non-zero |
| Valid but blocked | One-screen status plus the next high-level action or user prompt. | non-zero |
| Valid and ready | One-screen status plus `harness next` / `harness run` guidance. | zero |

Bare `harness` must not mention `.scratch/phase-state.json`, `state show`, `state repair`, or low-level `phase` commands in normal output.

## `harness run` Semantics

`harness run` is not an autopilot escape hatch and must not silently fuse approval plus execute.

It is the only normal command that may cross a workflow boundary, but every boundary crossing must be explicit and auditable:

1. If the next required action is read-only, `harness run` prints that action and does not mutate state.
2. If the next required action is human approval, an interactive TTY run may ask the user to approve the named plan and record explicit approval provenance.
3. If the caller is non-interactive or adapter/machine mode, `harness run` must return a blocked result and must not approve. Absence of `HARNESS_MACHINE=1` does not make non-TTY input safe; non-TTY human invocations are treated as blocked.
4. If approval is already recorded but execute prerequisites are missing, `harness run` must refuse and name the missing prerequisite in human terms.
5. If approval and execute prerequisites are satisfied, `harness run` may move to or continue execute using the same validator as the low-level lifecycle commands.

The approval prompt must be visibly separate from execute. A weak model must not be able to infer that calling `run` authorizes editing.

Human approval through `harness run` requires all of the following:

- stdin and the controlling terminal are real TTYs;
- the prompt is read from the controlling terminal, not piped stdin;
- the user sees the plan identity, phase, allowed path summary, and verification summary;
- the user must type `approve <plan-id> <challenge>`, where `<challenge>` is a fresh short random token printed in the prompt;
- bare `y`, `yes`, empty input, mismatched plan id, or stale challenge is rejected.

After recording approval, `harness run` stops and tells the user the next high-level command. It does not immediately continue into execute in the same invocation.

## `harness check` Contract

`harness check` is the normal no-flag readiness command. It is not the release gate and it is not the deep troubleshooting command.

Human mode checks:

- harness manifest/install consistency;
- required planning files and phase-state parseability;
- adapter prompt/artifact presence for installed adapters;
- whether current changes are inside `allowed_paths` when a git worktree is present and an execute gate exists;
- whether the current workflow state has an actionable next step.

Human output is concise and ends with either `OK` or the next high-level command to run.

Machine mode emits pinned JSON for the same normal checks:

```json
{
  "status": "ok|blocked|error",
  "may_edit": false,
  "checks": [],
  "next_command": "harness next",
  "next_user_prompt": null,
  "warnings": []
}
```

`release-check`, audit verification, migration verification, and deep drift diagnosis remain CI/advanced commands and are not part of normal `harness check`.

## Nonce and Approval Boundary

Nonce, trust, and anchor mechanics remain internal security implementation details for the normal path.

For human local approval through `harness run`, the CLI must satisfy the human-presence proof internally using the TTY challenge described above. If the proof cannot be satisfied, the human output must stop and tell the user to re-run `harness run` from a local interactive terminal.

For adapters and other machine callers:

- no nonce minting is automatic;
- no approval is created;
- the response is blocked until a human has completed approval through a human-facing TTY path;
- `may_edit` must remain `false`.

`approve-nonce`, `anchor`, and trust repair commands are advanced/security surfaces, not adapter happy-path commands.

## Human Output vs Machine Contract

Human commands print concise prose. Normal output must fit on one screen and avoid phase-state jargon.

Machine mode is explicit and stable. It is not inferred from TTY state.

v0.8.0 uses this machine-mode trigger:

```text
HARNESS_MACHINE=1 harness next
HARNESS_MACHINE=1 harness run
HARNESS_MACHINE=1 harness check
```

In machine mode:

- output is JSON only;
- adapters must treat any non-`ok` status as a stop;
- `may_edit=true` is legal only when the current state is execute-ready and approval is already valid;
- malformed state is a hard error;
- the schema is pinned by golden tests before adapter prompts are updated.

The existing `--json` flags may remain as compatibility/debug flags, but adapter prompts for v0.8.0 should use `HARNESS_MACHINE=1` so the normal command count does not grow and TTY auto-detection cannot change behavior.

Machine-mode schema additions are allowed only through golden updates in the high-level contract test slice. Human prose changes must not alter machine output.

## Error Scrub Rule

Normal human errors must not teach low-level internals as the first fix.

In README quickstart, onboarding, normal manual flow, adapter prompts, and normal command output, do not mention these as the primary next action:

- `.scratch/phase-state.json`
- `state show`
- `state repair`
- `phase set`
- `phase approve`
- `phase reopen`
- `approve-nonce`
- `anchor repair`
- `fsd-run-phase`
- `fsd-run-all`

Advanced sections may document these commands, but they must be clearly labeled advanced/debug/CI/security.

## Adapter Contract

Roo and OpenCode prompts must not inspect `.scratch/phase-state.json`, call low-level `phase` commands, or reason over durable pointers.

The adapter happy path is:

```text
HARNESS_MACHINE=1 harness next
HARNESS_MACHINE=1 harness run
HARNESS_MACHINE=1 harness check
```

Adapters may proceed with edits only if machine output says `status=ok` and `may_edit=true`.

If the response is blocked, adapters show the human-facing prompt returned by the contract and stop.

## Decisions

| Decision | User benefit | Safety impact | Compatibility impact | Why v0.8.0 |
| --- | --- | --- | --- | --- |
| Exactly four normal commands | Users can operate from a short transcript. | Reduces mistaken low-level command use. | Keeps old commands outside normal docs. | v0.8.0 is the UX simplification release. |
| Reject `mode` | Avoids a fifth concept before first success. | No safety loss. | Can be revisited later. | It violates the v0.8 command budget. |
| `run` can prompt for approval only in human TTY mode | Keeps approval visible without adding a fifth command. | Preserves explicit approval and blocks adapters. | Reuses existing approval validators. | Required to reconcile four commands with hard approval. |
| Machine mode uses `HARNESS_MACHINE=1` | Avoids TTY ambiguity and normal-user flags. | Makes adapter behavior deterministic. | Existing `--json` can remain. | Needed before adapter prompt rewrite. |
| Error scrub lint | Weak agents are not trained into internals. | Preserves hard boundaries by routing through high-level fixes. | Advanced docs still cover internals. | v0.8.0 changes the teaching surface. |

## Accepted, Rejected, Deferred Findings

Accepted blockers from Claude review:

- B1: `run` semantics were undefined. Fixed by the explicit state table above.
- B2: nonce and approval conflicted with the four-command rule. Fixed by human-only interactive approval and adapter blocking.
- B3: errors could leak internals. Fixed by the error scrub rule.
- B4: machine-mode trigger was unspecified. Fixed with `HARNESS_MACHINE=1`.
- B5: high-level JSON goldens must land before docs/adapters. Added as an implementation gate.

Accepted blockers from Claude re-review:

- B-NEW-1: `harness check` semantics were undefined. Fixed by the normal check contract above.
- B-NEW-2: bare `harness` absent/malformed behavior was undefined. Fixed by the bare-command state table.
- B-NEW-3: human approval recovery collided with the error scrub rule. Fixed by making TTY proof internal to `harness run` and routing failed proof to `harness run` from a real terminal.
- B-NEW-4: approval confirmation was underspecified. Fixed with controlling-TTY, plan-id, and random-challenge requirements.

Rejected:

- fused approve-and-execute for adapters;
- `check --worktree` as a normal happy-path requirement;
- `harness mode` in v0.8.0.

Deferred:

- deleting low-level commands;
- `phase back` / reopen UX as normal workflow;
- onboarding command;
- slash command discovery;
- heartbeat file;
- autopilot dry-run as normal workflow;
- browser dashboard and MCP server.

## Implementation Gates

Do not update adapter prompts before the high-level machine contract is tested.

Required implementation order:

1. Add or update tests for `HARNESS_MACHINE=1 harness next/run/check` JSON goldens.
2. Implement or adjust high-level command behavior.
3. Add tests for TTY-only approval confirmation and refusal of piped approval.
4. Add error scrub/doc grep tests for normal docs, normal output fixtures, and adapter prompts.
5. Update README and manual so simplified workflow appears first.
6. Update Roo/OpenCode prompts to use high-level machine flow.
7. Add UML internal architecture doc under `docs/`.
8. Add UML installed-user workflow doc under `docs/`.
9. Run specialist adversarial reviews for CLI/UX, workflow safety, adapter consistency, docs/onboarding, and release/CI.
10. Run release checks and ship only if blockers are accepted/fixed or explicitly rejected/deferred.

## Acceptance Checklist

- Normal user-facing commands count is four or fewer.
- Normal happy path has no flags and fits in one short copyable transcript.
- Adapter happy path uses high-level commands only.
- Adapter machine output never grants edit permission before approval and execute prerequisites.
- Human output and machine output are separate contracts.
- Normal docs and adapter prompts do not teach low-level phase/state/nonce/trust internals.
- Existing JSON, migration, trust, nonce, audit, adapter artifact, and slash-command contract tests still pass or are intentionally updated with matching goldens.
- README, manual, and required UML docs are updated.
- Final specialist plus Claude review has no unresolved ship blockers.
