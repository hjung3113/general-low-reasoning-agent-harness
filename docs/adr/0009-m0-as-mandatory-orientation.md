# Milestone 0 is the mandatory orientation phase

Every harness install begins at Milestone 0. M0 closes only when codebase orientation is complete — either via auto-detection (`harness recon` plus agent-filled judgment files) or via a grill-style interview that seeds project intent. `harness check` enforces this: M1+ workflow transitions are blocked until M0 done criteria pass. Done criteria are concrete and machine-checkable: all six core `.planning/codebase/` files at `status: current`, `ROADMAP.md` containing at least one future-milestone bullet, and `STATE.md` pointing at Milestone 1 (or explicitly recording "no future milestone").

The motivation is failure observed on M10: the M10 skill `workflow-codebase-recon` (renamed in M11 to `workflow-m0-orient`) instructed the agent to "run `harness recon` first" but did not enforce, and greenfield projects had no path at all. The result was incomplete orientation docs that downstream skill-packs (`workflow-tdd`, `workflow-code-review`, etc.) silently consumed with stale or empty anchors. Making orientation a phase rather than a skill optional turns this from a documentation problem into a workflow contract.

M0 is polymorphic by detection. The single public skill is `workflow-m0-orient` with two internal paths chosen by signal scan: Existing Code Path (lockfiles + source dirs present) runs `harness recon` and then fills judgment-heavy files (`CONVENTIONS`, `CONCERNS`, `ARCHITECTURE`, `SUMMARY`) by grepping the codebase and writing prose; Greenfield Path (no signals) runs a grill-style interview with the user to crystallize intent and produces the same eight-file shape with `source: human|mixed` instead of `detected`. The artifact contract from ADR-0008 does not change. Both paths close M0 by writing minimal skeletons (`NN-CONTEXT.md`, `NN-CHECKPOINTS.md`) under `.planning/milestones/NN-slug/` for every planned milestone in `ROADMAP.md`, giving the existing discuss/plan/execute flow stable targets to fill later.

A single skill with internal branches was chosen over a two-skill split (one for existing-code recon, one for greenfield seed) because the activation question — "is this a greenfield project?" — is the first decision agents face on a new install, and forking it across two skill names puts a consequential decision into the agent's skill-selection layer rather than into a deterministic detection step inside the skill. Codex R2 marked this 89 against R1's 92 for the two-skill split, with the architecture difference being that M0-as-contract was introduced after R1. The hybrid (one entrypoint, two internal sections) keeps the user-facing surface narrow without pretending detection and interview are the same operation.

Enforcement lives in `harness check`, not in convention alone. A new invariant fails closed: STATE active milestone > 0 with M0 criteria unmet → check exits non-zero. Skills also self-check at activation. CLI enforcement is the durable contract because skills can be bypassed but check runs on every gate transition.

This ADR is paired with a directory rename: the pre-M11 layout `.planning/phases/NN-slug/` becomes `.planning/milestones/NN-slug/`. The pre-M11 folders contained milestone docs, not phases of work — the rename eliminates a terminology collision between the workflow state machine (discuss/plan/execute/done, kept as "phase") and the work unit (kept as "milestone"). The rename is mechanical (175+ references across 54 files) and scripted; behavior is unchanged. The pre-M11 skeleton folder `00-planning-hydration` is absorbed into `00-orientation` to align the skeleton folder name with M0's user-facing purpose.

Reversal cost is moderate: collapsing M0 back to optional would mean removing the check invariant and reverting `workflow-m0-orient` to the M10 split (separate skills for existing-code orientation and greenfield seeding). The directory rename would need to be undone separately. Neither is destructive, but both touch the artifact contract and would require an explicit ADR supersede.
