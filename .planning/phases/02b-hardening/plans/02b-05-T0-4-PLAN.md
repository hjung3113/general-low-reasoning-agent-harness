## Scope

In scope:

1. Split `verification` into two fields in `.scratch/phase-state.schema.json`:
   - `verification: array<string>` — machine commands, each item MUST start with one of the 7 allowed verb prefixes.
   - `review: array<object>` — human evidence; each item is `{actor: string, at: ISO-8601-UTC, evidence_path: string, summary: string}`. All four properties required. `minItems: 0`. Required at top level of the schema (always present, possibly empty).
2. Replace `VERIFICATION_PREFIXES` in `scripts/lib/check.py:99-111` with exactly the 7 verbs from G4-A:
   ```
   ("python3 ", "git ", "jq ", "npx ", "pytest ", "harness ", "make ")
   ```
   Drop: `Validate `, `Review `, `Inspect `, `Confirm `, `Roo`, `core-only `, `OpenCode-only `, and `bash ` (D-G4).
3. Rewrite the validator at `scripts/lib/check.py:445-446` so the rejection diagnostic enumerates all 7 verbs inline AND cites `docs/protocol-spec.md#verification-allowlist`. Exact form (ADR-004 lines 366-368):
   ```
   {path} verification[{index}] = {value!r} does not start with an allowed verb.
   Allowed verbs: python3, git, jq, npx, pytest, harness, make.
   See docs/protocol-spec.md#verification-allowlist (source: scripts/lib/check.py VERIFICATION_PREFIXES).
   ```
4. Add a new `review` validator next to the verification validator: each item is a dict with the 4 required string keys, `at` matches the schema's ISO-8601-UTC timestamp pattern, `evidence_path` is permitted to be the empty-string sentinel (accepted, surfaced separately by `doctor`).
5. Add `doctor` finding: `"review entry has empty evidence_path"` (T0-4 acceptance per ADR-004 line 394). The finding is a WARNING, not a hard failure — the schema accepts empty `evidence_path`.
6. Add a one-shot migrator under `scripts/lib/state_migrate_t04.py` (callable from the T0-1 forward migrator) that, for every existing `verification[*]` string failing the new 7-verb allowlist, moves it into `review` with:
   ```
   {actor: <first-whitespace-delimited-token, or "migration" if empty>,
    at: <state.updated_at, or migration-time ISO-8601-UTC if absent>,
    evidence_path: "",
    summary: <original string verbatim>}
   ```
   The migrator removes the entry from `verification`. All writes go through the T0-A atomic primitive.
7. Update `.scratch/phase-state.json` and `.scratch/phase-state.example.json` to carry a `review: []` field (the live fixture's four `python3 ` entries already pass the new allowlist; no rewrite needed there).
8. Update `scripts/lib/check.py` semantic check so a `done` phase with `verification: []` AND `review: [<non-empty>]` is VALID (a phase closed by human review with no machine commands).
9. Add a regression test asserting `harness check` never executes a verification string (mock `subprocess.run` / `subprocess.Popen` and assert not called). This locks G4-B at the test surface.
10. Document the trust boundary as a header docstring in `scripts/release_smoke_test.py` (smoke runner explicitly executes verification entries on behalf of the developer; per G4-B boilerplate at ADR line 380).

Out of scope (delegated):

- Creating `docs/protocol-spec.md#verification-allowlist` itself — owned by T0-3 (per spec §7 row T0-3). T0-4's diagnostic CITES the anchor; T0-3 creates the document with a regression test asserting doc/constant parity.

## Acceptance Criteria

1. `scripts/lib/check.py:VERIFICATION_PREFIXES` is the exact 7-tuple `("python3 ", "git ", "jq ", "npx ", "pytest ", "harness ", "make ")`. No other prefixes are accepted.
2. The schema declares `review` as a required top-level array of `{actor, at, evidence_path, summary}` objects with the 4 keys required, `at` matching the existing UTC timestamp pattern, and all string values non-null. `verification` retains its `array<string>` shape with `minItems` relaxed (see #11).
3. Rejection diagnostic for a non-conforming `verification[i]` enumerates all 7 verbs inline on one line and cites `docs/protocol-spec.md#verification-allowlist` on the next line, naming `scripts/lib/check.py VERIFICATION_PREFIXES` as the source.
4. Rejection diagnostic for a non-conforming `review[i]` (missing key, wrong type, malformed `at`) names the offending key path (e.g., `review[2].actor`) and the violation kind (missing / wrong type / pattern).
5. The migrator (T0-4 component, invoked by T0-1 forward migration) relocates every `verification[*]` entry that fails the new allowlist into `review` with the synthesized object described in Scope item 6. Entries that pass the new allowlist remain in `verification` byte-for-byte.
6. `harness check` does NOT spawn a subprocess to execute any `verification[*]` string. A regression test mocks `subprocess.run`/`subprocess.Popen`/`os.system` and asserts they are NOT called from any code path reachable from `scripts.harness.main(["check"])`.
7. A `done` phase with `verification: []` and `review: [<≥1 well-formed entry>]` passes both schema validation and `check_phase_state_semantics`.
8. A `done` phase with `verification: []` and `review: []` FAILS (a closed phase must show evidence of either machine or human verification).
9. `doctor` emits a non-failing finding (warning code, e.g., `review_evidence_path_empty`) for any `review[i].evidence_path == ""`. Existing migrator-synthesized entries surface this finding.
10. `scripts/release_smoke_test.py` carries a header docstring stating the G4-B boilerplate (smoke runner treats verification entries as developer-trusted shell input).
11. Schema: `verification` keeps `items.type: "string"` and the existing pattern is REPLACED by enum/prefix validation done at the Python checker level (JSON Schema cannot easily express "starts with one of N prefixes" cleanly; the schema retains the string-array shape and the Python checker does prefix validation, matching the pre-slice split of responsibilities). `minItems` on `verification` is relaxed from `1` to `0`.
12. The live fixture `.scratch/phase-state.json` ends the slice with `"review": []` added and its four existing `python3 ` verification entries unchanged.

## Risks and Mitigations

- **Risk**: T0-1's forward migrator is not yet landed when T0-4 lands; the migrator function is unused. **Mitigation**: T0-4 ships `migrate_verification_to_review` as a pure function with its own test suite; T0-1 wires it in. The unused-import grep gate (if any) must allowlist this module.
- **Risk**: Existing tests in `scripts/test_harness.py` assume the old prefix list (e.g., a test asserting `"Validate X"` is accepted). **Mitigation**: step 1 enumerates the new test list; an explicit sweep at step 1 deletes or rewrites old-prefix tests with a NOTE in the test docstring citing this plan, mirroring the spec §9.1 pattern ("deleting a passing test is normally a smell; called out as intentional").
- **Risk**: A SKILL or roomode file under `.roo/` recommends `Confirm X` as verification. **Mitigation**: out-of-scope here (T1-S owns); but step 1 includes a grep across `scripts/test_harness.py` to confirm no in-scope test relies on the removed prefixes via fixture-loaded `.roo/` content.
- **Risk**: The mocked-subprocess test (#39) over-mocks and hides a legitimate subprocess call elsewhere in `check` (e.g., `git` calls in `check_changed_paths`). **Mitigation**: scope the mock to a context manager that wraps only the verification-validation code path; if `check` shells out for other reasons (e.g., `git` diff), the mock allows those by inspecting the first argv element and only failing when the argv prefix-matches a verification entry from the loaded fixture.
- **Risk**: The 3-line diagnostic is whitespace-sensitive; a future formatter run reflows it. **Mitigation**: test #16 asserts on substring presence, not exact whitespace; test #17/18 likewise substring-only.
- **Risk**: `additionalProperties: false` on `review[*]` breaks forward-compat if a future ADR adds a 5th key. **Mitigation**: accepted; adding a 5th key requires an ADR per spec §6 protocol, which is the same gate that would amend the schema in lockstep.

## Rollback Plan

If T0-4 lands and a downstream slice (T0-3, T1-S) discovers an incompatibility before the bundle ships:

1. Revert the schema change first (`git revert` the schema commit). The validator continues to accept the old shape because the constant change is in a separate commit.
2. Revert the constant change (`VERIFICATION_PREFIXES`) second. This restores acceptance of the old prefixes. Live fixture is unaffected (all entries are `python3 `).
3. The migrator module is dead code at this point; leave it in place (deletion is a separate cleanup commit).
4. The smoke-runner header docstring is text-only and safe to leave.

Order matters: reverting the constant before the schema would leave the schema requiring `review` while the checker rejects new soft-prefix entries that pre-existed; reverting the schema first restores the looser shape before re-loosening the checker.

{
  "phase": "done",
  "verification": [
    "python3 -m unittest scripts/test_harness.py",
    "harness check"
  ],
  "review": [

No subprocess is spawned. Result: pass.

## Integration and Hand-off Notes

- T0-1's forward migrator imports `from scripts.lib.state_migrate_t04 import migrate_verification_to_review` and calls it after bumping `state_schema_version` but before the atomic-write. T0-1 owns the wiring; T0-4 ships the pure function and its tests.
