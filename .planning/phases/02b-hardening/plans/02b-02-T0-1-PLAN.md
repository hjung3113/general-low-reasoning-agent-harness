## Plan ID

02b-02-T0-1

## Goal

Align the `phase=done` contract across schema, checker, live state, tests, and docs to ADR-001 option 3 (drop `approved` constant from the `done` branch). Introduce `state_schema_version` at the top level of the schema with the value `2` written by the forward migrator (pre-slice records treated as version `0`). Ship a migrator (`scripts/lib/migrate.py` + `scripts/migrate_state.py` invoked via `harness migrate state {--forward,--reverse,--resume}`) implementing the 4-step protocol (sidecar via T0-A → `.bak` via `O_EXCL` → new target via T0-A → delete sidecar). Convert the live `.scratch/phase-state.json` (currently `phase=done, approved=false`, no `state_schema_version`) onto the new shape via the forward migrator. Encode the ADR G2-B transition state machine as a small data table consulted by the checker for static validation. Document the breakage under `## Unreleased (develop)` → `### Breaking` in `CHANGELOG.md`.

## Acceptance (verbatim from spec §7 T0-1 row + sub-requirements + §9 + §11 acceptance + Artifact 5 §"Migrator acceptance tests")

- `phase=done` contract aligned across schema, checker, live state, docs, tests; introduce `state_schema_version`; migrator with `--reverse`. (§7 row T0-1)
- Sub-requirement: introduce the `state_schema_version` field in the schema with initial value `1`. The ADR-001 chosen `done` shape bumps the value (to `2`). The ENFORCEMENT GUARD (refuse newer versions) is NOT in this row; it is deferred to `02c-hardening`. (§7 T0-1)
- Sub-requirement: the migrator writes `.scratch/phase-state.json.pre-<old-schema-version>.bak` BEFORE calling `os.replace`. The backup is byte-identical to the pre-migration file. (§7 T0-1 — and per ADR G1-D the backup is RELOCATED to `.harness/backups/<basename>.pre-repair.<ISO-8601-nanos>.<pid>.bak`; this PLAN follows the ADR location.)
- Sub-requirement: the migrator supports `--reverse` for at least the version 1 → 0 downgrade path. The downgrade path MAY drop fields the older shape did not understand; it MUST NOT silently corrupt. Per ADR-001 sub-decision 3a, `--reverse` writes `approved=false` for `done` records. (§7 T0-1; ADR-001 sub-decision 3a; Artifact 5 `--reverse`)
- Sub-requirement: all state writes performed by the migrator use the T0-A primitive. (§7 T0-1)
- Sub-requirement: the existing test that asserts "`done` requires `approved=false`" (`scripts/test_harness.py`) MUST be deleted or rewritten. (§7 T0-1 / §9.4)
- Sub-requirement (migrator order-of-operations, 4-step protocol): (1) write `.resume.json` sidecar via T0-A; (2) write `.bak` via `os.open(..., O_WRONLY|O_CREAT|O_EXCL, 0o644)`; on `FileExistsError`, abort with diagnostic instructing `harness migrate state --resume`; (3) write the new target shape via T0-A; (4) delete the sidecar. (§7 T0-1; ADR G1-E)
- Sub-requirement (CHANGELOG `### Breaking` skeleton): ensure `CHANGELOG.md` exists at repo root with a `## [Unreleased]` (or already-present equivalent unreleased) section containing a `### Breaking` subsection. Append the `done` contract change and the `state_schema_version` introduction. Backfilling historical versions is OUT of scope. (§2.4; §7 T0-1; §13 condition 9)
- §11 / Artifact 5 round-trip property: `json.loads(forward(x)) == json.loads(reverse(forward(x)))` MUST hold for the current live fixture.
- §11 / Artifact 5 acceptance: `--forward` is idempotent at the `json.loads` level; the `.bak` is byte-identical to the input; migrator REFUSES to overwrite an existing `.bak` (exit 1); `--resume` happy path with sidecar present and target hash equal to `pre_hash` re-runs cleanly.
- Transition state machine (G2-B): every `(from, to)` pair is consulted; the checker rejects undefined transitions (exit 2) and rejects `plan→execute` / `execute→done` without `approved=true` from a prior approve call, and rejects backward / lateral transitions without `--reset-approval`. T0-1 lands the DATA TABLE + a checker hook reading it; the CLI verb that consumes it for runtime transition writes is T0-3 (not this row). T0-1 acceptance covers static validation only.
- Reversibility: `partial`. The live state is rewritten to the new shape; `--reverse` migrator + `.bak` artifact are the mitigations. (§7)

## Risk + reversibility

- **Reversibility: partial.** The live state is rewritten to v2 in commit D. Recovery path: `python3 scripts/migrate_state.py --reverse` produces a `json.loads`-equal pre-image of the pre-migration record (per T-11 acceptance and Artifact 5 round-trip property). The `.bak` artifact under `.harness/backups/` is byte-identical to the pre-migration file and can be `cp`-restored if `--reverse` is itself broken.
- **Risk: schema rejection cascade.** After A2 lands, every consumer of `.scratch/phase-state.json` that does not set `state_schema_version=2` is rejected by `check.py`. The live fixture is migrated in the same PR (commit D); but any other repo running `python3 scripts/harness.py check` against a pre-slice state will fail with the migration prompt — this is INTENDED per T-7 but is a breaking change. CHANGELOG entry (commit E) names this explicitly.
- **Risk: `.bak` accumulation.** ADR G1-D specifies a 10-most-recent retention cap with auto-pruning. T0-1 implements the cap; tests T-13/T-14 cover happy/race paths but NOT retention pruning specifically — flagged for T0-5 (which owns `state_repair` backup-writing and shares the retention helper). T0-1 calls the same helper; if the helper is not yet extracted, T0-1 inlines it and T0-5 refactors. **Decision: extract `lib.backups.write_backup_with_excl_and_prune` in T0-1 commit C** so T0-5 can consume it without churn.
- **Risk: sidecar orphaning if test crashes mid-run.** `pytest`'s `tmp_path` isolates these; the production code path uses real `.harness/backups/` only on the live fixture migration (commit D), executed once with manual verification.
- **Risk: ADR-001 sub-decision 3a misimplementation.** T-19 explicitly tests `--reverse` writes `approved=false`; T-11 tests round-trip equality of the live fixture (which has `approved=false` pre-migration). If 3a is mis-coded as 3b (`approved=true`), T-11 fails because the live fixture's `approved=false` would not round-trip.
- **Risk: `state_schema_version` introduced as `1` then bumped (per §7 T0-1 literal wording) vs. introduced directly as `2`.** Spec §7 says "initial value `1`. The ADR-001 chosen `done` shape bumps the value (e.g., to `2`)." ADR-001 Decision § resolves this: "Bump `state_schema_version` from `1` (the value T0-1 introduces) to `2` for the new `done` shape. Pre-T0-1 records (which have no `state_schema_version` field) are treated as version `0`." **PLAN decision: introduce the field directly at value `2` in commit A**, because no v1 record will ever exist in the wild (the spec wording reflects a logical sequence within T0-1, not a wire-format intermediate state). The migrator treats absent-field as v0 and writes v2 — there is no v1 transition. Documented in CHANGELOG bullet 2.
- **Risk: heading-rename creep.** This plan deliberately preserves `## Unreleased (develop)` and does not normalize to `## [Unreleased]`. T-27 / T-28 are written against the literal `## Unreleased (develop)` string so they pin the current heading and force a future T3 change to update both heading and tests together.
